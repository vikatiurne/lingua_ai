## 🔧 Схема

```prisma
model TopicProgress {
  id            String         @id @default(cuid())
  userId        String
  user          User           @relation(fields: [userId], references: [id], onDelete: Cascade)

  level         CEFRLevel
  topicName     String

  status        ProgressStatus @default(not_started)
  score         Float?
  attempts      Int            @default(0)
  lastPracticed DateTime?

  createdAt     DateTime       @default(now())
  updatedAt     DateTime       @updatedAt

  @@unique([userId, level, topicName])
  @@index([userId, level])
  @@map("topic_progress")
}

model ExerciseProgress {
  id            String         @id @default(cuid())
  userId        String
  user          User           @relation(fields: [userId], references: [id], onDelete: Cascade)

  level         CEFRLevel
  topicName     String
  subtopicName  String
  templateId    String

  status        ProgressStatus @default(not_started)
  score         Float?
  attempts      Int            @default(0)
  lastPracticed DateTime?

  createdAt     DateTime       @default(now())
  updatedAt     DateTime       @updatedAt

  @@unique([userId, level, topicName, subtopicName, templateId])
  @@index([userId, level])
  @@map("exercise_progress")
}
```

**`User`:**
```prisma
model User {
  ...
  topicProgress     TopicProgress[]
  exerciseProgress  ExerciseProgress[]
}
```

### Відхилення / рішення
- **Не запускав `prisma migrate dev`**, як написано в алгоритмі задачі. Причина: AGENT_RULES §7.12 — Strapi й Prisma ділять одну БД, `migrate dev` бачить Strapi-таблиці як drift і пропонує `reset` (знищить дані). Натомість:
  1. згенерував SQL через `prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --shadow-database-url …` (окрема shadow-БД, основні дані не читаються);
  2. записав `migrations/20261017000000_split_progress_tables/migration.sql`;
  3. застосував `pnpm --filter web db:deploy`.
  Результат той самий, Strapi-таблиці не зачеплені.
- **Backup зроблено** перед міграцією (`pg_dump`). `user_progress` була порожня (0 рядків), тож data-migration не потрібна — таблиця просто видалена.
- **Додано 2 unit-тести для `persistGaps`** (мок `topicProgress`). У задачі 20 таких тестів не було — лише `analyzeGaps`, тож «оновити тести» фактично означало «додати покриття `persistGaps` без `""`-хаку».
- **Ідемпотентність перевірено на живій БД** тимчасовим інтеграційним тестом (створення/видалення тестового user): два `persistGaps` поспіль → 2 рядки на 2 теми, статус `in_progress` не скидається; `exerciseProgress` дозволяє дві підтеми однієї теми. Тест видалено після перевірки (поза scope).
- **README не змінювався** — жоден пункт статусу не завершується цією chore-задачею.
