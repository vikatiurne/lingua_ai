## 🧩 Реалізація

### 1. Ключ ідентичності теми
У моделі `Exercise` немає `topicId` (тема зберігається як `level` + `topicName` +
`subtopicName`), тому «одна на тему» реалізовано по цих чотирьох полях.

### 2. Чому без фільтра по `status`
Умова «оновлювати тільки `in_progress`» лишала б дірку: завершена (`evaluated`)
review-вправа не знаходилась би, і кожен новий клік створював би ще один запис.
Тому знайдений запис **завжди** перезаписується (скидання оцінок і `completedAt`
повертає його в робочий стан).

### 3. Захист на рівні БД
Prisma не вміє виразити partial unique index, тому він живе тільки в міграції:

```sql
CREATE UNIQUE INDEX "exercises_one_review_per_topic_idx"
ON "exercises" ("userId", "level", "topicName", COALESCE("subtopicName", ''))
WHERE "isReview" = true;
```

Наслідок: `prisma migrate diff` буде пропонувати його дропнути — ігнорувати.
`prisma migrate dev/reset` заборонені (спільна БД зі Strapi), тільки `migrate deploy`.

### 4. Міграції
- `20261022120000_add_exercise_is_review` — колонка + індекс.
- `20261022140000_unique_review_per_topic` — SQL-дедуп (лишає найновіший
  `isReview = true` на тему) + partial unique index.

### 5. Очищення старих дублікатів
`pnpm cleanup:reviews` — dry-run; `pnpm cleanup:reviews --apply` — видалення.
Якщо тема вже має `isReview = true`, усі legacy-копії теми видаляються.

## 🔧 Хрупкі місця (обов'язково)

### 1. Оновлення (Update) замість створення (Create)
Використовується `prisma.exercise.update` для знайденого запису — `create` лише
коли review-вправи для теми ще немає.

### 2. Гонка запитів
Два одночасні POST-и могли б пройти `findFirst` до `create`; partial unique index
ловить такий випадок. Другий запит отримає помилку унікальності (500) — при
повторному кліку користувач просто потрапить у вже створену вправу.

### 3. Очищення історії (Опційно)
Одноразовий скрипт уже доданий; запускати його потрібно **до** застосування
міграції з unique index, інакше індекс не створиться на дублікатах (у міграції
дедуп уже вбудований).
